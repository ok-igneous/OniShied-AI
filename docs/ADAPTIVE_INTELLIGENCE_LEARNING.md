# Adaptive Intelligence Learning — Technical Contract

**Status:** Accepted design direction; not implemented.
**Initial scope:** Learn from AI investigation outputs, verified incident outcomes, operator corrections, and approved external intelligence without granting AI direct mutation or response authority.

## 1. Objective

OniShield must become more effective over time while retaining a deterministic, AI-independent protection path. AI models may propose reusable knowledge. OniShield's own learning pipeline validates, versions, tests, approves, distributes, and can roll back that knowledge before the native engines consume it.

"Learning" in the initial release means controlled acquisition of knowledge artifacts and detection improvements. It does **not** mean allowing a model to rewrite production code, silently change model weights, or autonomously promote its own output.

## 2. Learning sources

1. **AI investigations:** candidate indicators, behavioral patterns, correlations, detection hypotheses, benign alternatives, and investigation playbooks.
2. **Incident outcomes:** whether a finding was confirmed, benign, unresolved, contained, or later disproved, with evidence and outcome provenance.
3. **Operator feedback:** authenticated corrections, dispositions, false-positive reports, and explicit approvals.
4. **Approved threat intelligence:** licensed feeds and curated sources with source identity, timestamps, expiry, handling restrictions, and provenance.
5. **Controlled lab results:** synthetic and authorized test events, replay results, and red-team exercises.

Every item must retain its source, collection time, tenant scope, originating model/provider and model version where applicable, prompt/contract version, evidence references, and validation history.

## 3. Knowledge artifact types

The learning pipeline may propose typed artifacts such as:
- Indicator candidates (IP, domain, URL, file hash, or other explicitly supported types).
- Behavioral pattern candidates and detection-rule proposals.
- Correlation and enrichment mappings.
- Investigation playbook suggestions.
- Benign-pattern and suppression candidates.
- Confidence rubric or detection coverage recommendations.

An artifact is not active intelligence merely because it was generated by AI. Indicator candidates must use the existing pending/review lifecycle. Detection-rule proposals must be represented as versioned, declarative, bounded rules—not executable code or arbitrary queries.

## 4. Pipeline and trust boundaries

1. **Capture:** accept a bounded, schema-validated candidate from an authorized investigation or feedback workflow.
2. **Quarantine:** store it as pending, immutable input with provenance and tenant scope.
3. **Validate:** enforce type-specific syntax, evidence references, source trust, expiry, licensing, TLP/handling restrictions, and tenant authorization.
4. **Deduplicate and correlate:** identify existing artifacts and conflicts without merging across tenants.
5. **Test:** replay the proposed artifact against versioned historical and synthetic datasets, including benign counterexamples and adversarial fixtures.
6. **Review:** require an authorized human reviewer for activation in the initial release. AI cannot approve its own candidate.
7. **Publish:** create an immutable, signed/versioned knowledge package and activate it only through a deterministic service authorization path.
8. **Monitor:** measure true/false positives, missed detections where known, coverage, performance cost, and customer impact.
9. **Rollback or revoke:** support immediate disablement, reasoned audit records, and replay of the previous known-good version.

Model output and source evidence are untrusted data. Prompt instructions inside logs, feeds, tickets, filenames, or model responses must never change pipeline policy, scope, permissions, or tool access.

## 5. Native intelligence integration

The deterministic detection engine may consume only active, validated, compatible knowledge artifacts. Every finding must record the exact rule/knowledge version used so that it can be reproduced.

Native protection must continue if every AI provider is unavailable. The knowledge base and active detection packages must be locally/cache available to the relevant enforcement component, with integrity checks and expiry behavior defined. AI availability must never be a prerequisite for evaluating an already-approved rule.

A candidate must not directly change severity, confidence, Autopilot permissions, allowlists, risk ceilings, or action authorization. A threat-intelligence match or model confidence score is evidence—not proof of compromise and never permission to block.

## 6. Tenant privacy and shared learning

- Tenant-derived artifacts are private to that tenant by default.
- No raw customer events, logs, identifiers, secrets, or investigation text may be shared across tenants by default.
- Cross-customer learning is a separate, explicit opt-in program with contractual disclosure, data minimization, de-identification, provenance, review, and revocation controls.
- De-identification must be assessed for re-identification risk; removing names alone is insufficient.
- Global intelligence requires a separate namespace, authorization model, reviewer process, licensing/redistribution review, and database isolation policy. Never represent global scope using a null or special tenant ID.
- Respect TLP and source licensing. TLP is not an authorization substitute.

## 7. Model learning versus knowledge learning

**Initial release:** use knowledge learning—validated indicators, declarative rules, mappings, and playbooks. This is explainable, auditable, provider-independent, and reversible.

**Later research only:** fine-tuning or training models on curated examples may be considered after explicit data rights/consent, privacy review, dataset lineage, contamination checks, held-out evaluations, model versioning, rollback, and cost analysis. Do not send customer data to provider training by default or claim that an API model learns permanently from an ordinary request.

## 8. Required controls

- Strict Zod schemas and bounded payload/record/compute budgets.
- Server-derived actor and tenant context; never trust model-supplied identity.
- Append-only candidate, review, activation, and rollback audit.
- Separation of candidate submission, review, and publication permissions.
- Immutable artifact versions, signatures/digests, expiry, and revocation.
- Replay tests with benign and malicious fixtures; regression gates for false positives.
- Kill switch to disable newly learned packages without disabling the base deterministic engine.
- No arbitrary code, shell, SQL, network access, or response-action capability in the learning worker.
- No automatic activation in the initial release; human review is mandatory.
- Customer-visible disclosure and controls for any future shared-learning program.

## 9. Acceptance criteria

1. AI can submit a schema-valid candidate but cannot activate, edit, or revoke it.
2. Candidate provenance and evidence references are persisted and tenant-scoped.
3. Invalid, expired, unsupported, unlicensed, or cross-tenant candidates are rejected or quarantined.
4. Replay tests demonstrate that a candidate improves target detection without exceeding an explicitly approved false-positive budget.
5. A reviewer can approve/reject with reason and authenticated attribution.
6. Published packages are immutable, versioned, integrity-checked, and reproducible.
7. Rollback restores the previous active package and is audited.
8. AI provider outage does not interrupt native evaluation of active knowledge.
9. Cross-tenant data remains isolated unless a separately approved opt-in sharing design is implemented and tested.
10. No learning output can independently authorize an Autopilot or destructive response action.

## 10. Delivery sequence

1. Define candidate schemas and append-only persistence.
2. Build quarantine, provenance, deduplication, and tenant isolation.
3. Add operator review and activation lifecycle.
4. Add deterministic replay/evaluation harness and false-positive gates.
5. Publish signed/versioned knowledge packages to native detection.
6. Add outcome feedback and monitored rollback.
7. Consider opt-in shared intelligence only after privacy, licensing, and global-namespace design review.

This contract does not change current implementation status. Until each acceptance criterion is implemented and verified, adaptive learning must be described as planned—not as a working capability.
